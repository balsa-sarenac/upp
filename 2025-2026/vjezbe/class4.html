Подсетник са претходног часа

Већ смо видели:

  • Основне BPMN елементе у Бонити:
    • Start / End events
    • User / Service / Script tasks
    • XOR и AND gateways
    • Pools и swimlane-ови
  • Минималан процес:
    • Start → (User task) → (Script/Service) → End
    • повезан са actors и BDM-ом

Данас идемо даље ка реалнијим и робуснијим процесима.

Зашто причамо о грешкама и deadlock-овима?

  • Реални процеси су:
    • дужи,
    • имају више грана,
    • имају више учесника
  • Без пажње:
    • лако се направи „замка“:
      • процес чека нешто што никад не стигне
      • нека грана никад не може да се догоди
  • Циљ:
    • да препознате и избегнете најчешће BPMN „грешке“ (smells)

Deadlock – шта је то у контексту BPMN?

  • Познат из конкуретног програмирања:
    • два или више процеса чекају један другог → нико не напредује
  • У BPMN-у:
    • комбинација gateway-а, догађаја и токова
    • доводи до тога да инстанца процеса „заглави“ и никад не дође до end event-а
  • У Бонити:
    • видећете инстанцу која је „у току“, али јој се ништа не дешава

Типичан извор deadlock-а: погрешан AND gateway

Пример:

  1. AND split – процес се грана на две паралелне гране
  2. На једној грани се налази услов који није увек задовољен
  3. AND join – чека да обе гране стигну
  4. Ако једна грана никад не стигне → процес заглави

Лекција:

  • AND join мора бити сигуран да ће све гране увек моћи да стигну
  • Ако не, можда треба XOR/Inclusive gateway или друга структура.

Типична грешка: погрешно коришћење gateway-а

  • Gateway није „украшени чвор“:
    • сваки излазни ток мора имати јасну логику
  • Лоши обрасци:
    • више излазних стрелица из task-а без gateway-а
    • XOR gateway са гранама које немају услов/подразумевани ток
    • Parallel gateway где једна грана заправо није паралелна, већ условна

Препорука:

  • за сваку одлуку:
    • најчешће XOR gateway
    • јасно наведени услови или default грана

Типична грешка: unreachable task-ови

  • Task који:
    • нема ниједан улазни ток
    • или се налази у грани до које никад не води важећи услов
  • Последица:
    • тај део процеса се никада не извршава
  • Како препознати:
    • визуелни преглед дијаграма
    • гледање у Portal-у: да ли се тај task икад појави?

Типична грешка: процес без јасног краја

  • Нема end event-а:
    • инстанца формално никад не заврши
    • тешко је мерити трајање и „успешан завршетак“
  • Превише end event-ова без јасног значења:
    • „End1“, „End2“, „End3“ без описног назива
  • Препоруке:
    • сваки процес мора имати бар један end even
    • ако има више:
      • јасно их именовати (нпр. „Approved“, „Rejected“, „Cancelled“)

Колаборација процеса: зашто нам треба?

У реалним системима:

  • Не решавамо све једним огромним процесом
  • Имамо:
    • више процеса који сарађују
    • део логике који желимо да поново искористимо
    • различите „учеснике“ (организације, системи)

Примери:

  • Процес „Отвори аукцију“ позива процес „Прикупљање понуда“
  • Процес „Обрада рекламације“ позива процес „Рефундација новца“

Начини колаборације (BPMN perspective)

У BPMN-у:

  • Више pool-ова:
    • сваки представља посебан процес / систем / организацију
  • Комуникација:
    • преко message flow стрелица
  • У Бонити:
    • најчешће користимо:
      • call activity (један процес позива други)
      • или message/signal event-е (напредније, наредни час)

Данас: фокус на call activity.

Call Activity: идеја

  • Call activity:
    • task у процесу који позива други процес (sub-process)
  • Користи се за:
    • поновну употребу истог процеса на више места
    • одвајање сложенијег дела у посебан процес
  • Позвани процес:
    • може имати своје start/end, своје actor-е и BDM

Call Activity у Бонити (основни кораци)

У Bonita Studio-у:

  1. Креирати суб-процес (pool)
  2. У главном процесу:
    • додати call activity у дијаграм
  3. У својствима call activity:
    • изабрати који процес се позива
    • подесити мапирање података (input/output)
  4. Deployment:
    • водити рачуна да су оба процеса deploy-овани

Догађаји (events) – шира слика

До сада:

  • Start / End events

Следећи корак:

  • Intermediate events:
    • нешто се дешава у току процеса
  • Boundary events:
    • „качe“ се на task/subprocess
    • реагују ако се деси одређени догађај (нпр. грешка, timeout)

Типови које ћемо видети:

  • Timer even
  • Error even

Timer events (тајмери)

  • Када су корисни:
    • дефинисање рокова
    • подсетници
    • ескалације (нпр. ако нико не обради захтев X дана)
  • Два типична начина употребе:
    1. Intermediate catching timer event:
      • процес чека одређено време пре наставка
    2. Boundary timer event:
      • постављен на user task
      • ако рок истекне, активира ескалација/алтернативни ток

Пример: boundary timer на user task-у

Scenario:

  • User task: „Approve auction“
    • Assigned to manager
  • Boundary timer event:
    • ако менаџер не реагује за 3 дана:
      • процес иде у алтернативни ток:
        • подсетник,
        • промена assignee-а,
        • аутоматско одбијање/одобравање, итд.

BPMN:

  • User task са малим clock иконицом „прикаченом“ са стране.

Error events (грешке)

  • Када користимо:
    • када желимо да ухватимо грешке током:
      • извршења конектора,
      • сервисних/скрипт task-ова,
      • позваних процеса
  • Boundary error event:
    • прикачен на task/subprocess
    • ако се деси грешка -> прекида task
    • ток иде у алтернативну грану (errror handling)

Пример:

  • Service task „Call payment service“ + boundary error even → ако сервис врати грешку, идемо у ручну обраду.

Типичне грешке са догађајима

  • Заборављени boundary event:
    • дода се на task, али се не повеже даље
  • Без јасне логике после догађаја:
    • нпр. timer активира ток који никуд не води

Препорука:

  • користити догађаје тамо где постоји јасна пословна потреба
  • проверити:
    • има ли смислен крај после тог догађаја?
    • да ли можемо да објаснимо „шта се дешава када“ у 2–3 реченице?

Примењено на пројекат

Где можете да употребите:

  • Call activity:
    • main процес -> sub-процес за одређену фазу
    • main процес -> sub-процес за секвенцу која се понавља на више места
  • Timer events:
    • временски рок за кодификацију
    • временски рок за одговоре владе
  • Error events:
    • грешка при слању мејла
    • грешка у позиву спољног сервиса (ако га имате)

Мини провера за BPMN квалитет

Пре него што предате модел:

    • догађаја (timer/error) или
    • call activity, ако је потребно?
